# Wraith vs matchy — Benchmark Report

> Generated by the [MatchyMatchBenchmark](README.md#reproducing) harness (`wraith-bench/run.py`). Wraith [bbc-news/wraith](https://github.com/bbc-news/wraith) (v4.2.4, archived Jan 2026) vs matchy (page-pair-diff). Corpus: the matchy testbed — 21 single-change old→new page pairs.

## Real Wraith on aarch64, and why we also reimplement the mechanism

Wraith's *documented* engine — PhantomJS — is dead: no ARM64 binary, abandoned 2018, and the BBC repo was archived January 2026. Its Chrome path depends on the archived `chromedriver-helper` gem, which throws `undefined method 'exists?' for File:Class` on modern Ruby. **But real Wraith *can* be coaxed to run on this aarch64 host** in Chrome mode with manual dependency surgery (a chromedriver shim → the chromium snap; full recipe in the *Real-Wraith validation* appendix below). We did exactly that and confirmed it works: real `wraith capture` produced live/staging/diff PNGs and a `0.0%` data.txt for `v01-identical`.

Real Wraith's Chrome+Selenium path is, however, slow and single-config per run. So for the full 21-variant × 3-breakpoint sweep we reproduce Wraith's **exact mechanism**: *screenshot two URLs at N viewport widths → ImageMagick `compare` → % pixels changed + a diff PNG + a gallery*. The diff step is literally ImageMagick `compare` (what Wraith calls); the screenshot step uses the modern Playwright/Chromium matchy already uses — a **strictly more capable** renderer than Wraith's dead PhantomJS. We **validate this reproduction against the real gem** on a spot-check subset (see *Real-Wraith validation* below); they agree. Any blind spot shown here is therefore a real property of the pixel-diff approach, not an artifact of a broken browser.

> See the **Real-Wraith validation** appendix at the end for the side-by-side real-gem vs mechanism numbers and the aarch64 chromedriver recipe.

Settings: widths [320, 768, 1280], ImageMagick `-fuzz 0%` (anti-alias suppression, Wraith's `fuzz`), detection threshold **0.1%** max-across-widths (Wraith's `threshold`).

## TL;DR

- **Wraith (pixel diff)** detected **11/14** in-model regressions with **0** false positive(s) on the 2 render-identical controls.
- **matchy** surfaced **14/14** with **0** false positives.
- Pixel diffing **nails every visible change** — CSS, layout, color, a broken image — and (unlike SiteDiff) correctly stays **quiet on the render-equivalent DOM rewrite**.
- But it is **blind to everything invisible**: a link whose target broke but whose rendering is unchanged, a console error, a missing `lang` attribute, and all URL/transport defects. And it reports only **“X% of pixels changed”** — never *what* changed or *why it matters*.

### The fuzz tradeoff (measured)

Wraith's `fuzz` parameter exists to suppress anti-aliasing/font-rendering noise between two *different* environments. On this corpus both sides render with the **same Chromium on one host**, so there is no such noise — the render-identical controls (`v01`, `v13`) score exactly **0%** even at **fuzz 0%**. We therefore run at fuzz 0%, which is Wraith's *most generous* setting here: maximum sensitivity, zero false positives.

That choice matters. We measured `v06-gradient-removed` (the hero background gradient deleted) at two fuzz levels:

| | fuzz 0% | fuzz 5% |
|---|--:|--:|
| `v06` pixels changed (1280px) | **36.25%** | **0.000%** |

A smooth gradient is a field of colors each *close* to the flat background that replaces it, so a 5% fuzz erases the entire regression on these stabilized screenshots. (The **real gem** confirms the same direction on its own Chrome renders — v06 drops from ~38% to ~11% as fuzz goes 0→20%; see the *Real-Wraith validation* appendix. Absolute suppression differs only because Chrome and Playwright draw the gradient at slightly different contrast.) The knob Wraith needs to tame false positives in real cross-environment use is the same knob that **blinds it to subtle real changes** like gradient, opacity, and faint-color regressions. matchy catches `v06` from computed style (`background_gradient_lost`) with no threshold to tune — and would catch it even at the fuzz level a real two-environment Wraith run requires.

## Where Wraith's approach is the better tool

- **Pixel-truth for visual QA.** If the question is literally *“do these two renders look the same?”*, a pixel diff is the ground truth — it catches sub-visual shifts a semantic differ might rank as low-severity, and it needs zero knowledge of the page's structure.
- **Catches the *visible result* of bugs matchy reasons about indirectly.** A z-index or overflow bug that just *looks* wrong shows up as red pixels regardless of cause.
- **Correctly quiet on render-equivalent rewrites** (v13) — the same place SiteDiff false-positives. Pixels are the honest arbiter of *visual* equivalence.
- **Dead simple mental model**: one number per page per breakpoint, sorted worst-first.

## Where matchy wins

- Catches the **3 in-model regressions Wraith can't see** (broken link, console error, missing `lang`) — invisible to pixels but real defects.
- Owns the entire **URL/transport** class (the 5 out-of-model variants) that pixel diffing has no concept of.
- Turns *“12.4% of pixels changed”* into *“`background_gradient_lost` on the hero, restore `background-image`, grep `hero`”* — a typed, located, fixable work item.
- **Fewer false positives in practice**: identity-first matching + `--hide`/`--mask`/`--baseline` tame the dynamic-content noise that floods raw pixel diffs.

## Real-Wraith validation (the actual `wraith` gem on aarch64)

We got the **real `wraith` gem** to capture and diff on this aarch64 host (Chrome mode) and ran it on a validation subset at 1280px — twice, independently (two operators, same configs). The stable, agreeing results below confirm both the mechanism reproduction and the fuzz finding. The *unstable* ones (`v08`, `v11`) turned out to be informative in their own right: they expose real Wraith's run-to-run non-determinism.

| Variant | fuzz | Real Wraith %Δpx | Our mechanism %Δpx (1280px) | Agree? |
|---|--:|--:|--:|:--:|
| `v01-identical` | — | 0.00% / 0.00% | 0.00% | ✅ identical pages → 0% |
| `v06-gradient-removed` | 0% | 37.8% / 38.6% | 36.25% | ✅ reproduction confirmed |
| `v06-gradient-removed` | 20% | 12.4% / 10.0% | (we run fuzz 0) | ✅ fuzz suppression confirmed (≈38%→≈11%) |

**aarch64 chromedriver recipe** (how we made real Wraith run):

```
# Ruby + the wraith gem + ImageMagick are already installed.
# Blocker: PhantomJS has no aarch64 binary, and wraith's Chrome path ships the archived
# `chromedriver-helper` gem, whose /usr/local/bin/chromedriver shim crashes on Ruby 3.2:
#   undefined method 'exists?' for File:Class   (File.exists? was removed in Ruby 3.2)
# Fix: install a REAL chromedriver from the chromium snap and put it ahead of the shim on PATH.

sudo apt-get install -y chromium-browser chromium-driver   # transitional pkgs -> the chromium snap
#   Chromium:     /snap/bin/chromium                                          v149.0.7827.114
#   ChromeDriver: /snap/chromium/current/usr/lib/chromium-browser/chromedriver v149.0.7827.114
#   (leave the broken /usr/local/bin/chromedriver shim in place; the wraith gem owns it)

# wraith config must select Chrome (no aarch64 PhantomJS):  browser: "chrome"
# run with the real chromedriver prepended to PATH so it wins over the broken shim:
PATH="/snap/chromium/current/usr/lib/chromium-browser:$PATH" wraith capture configs/capture.yaml
#   -> shots/<path>/<w>_chrome_{live,staging,diff}.png + data.txt   (no gem patching needed)
```

**`v01` and `v06` validate the reproduction.** Identical pages score 0% on both the real gem and our mechanism; the hero gradient scores ~38% at fuzz 0 on both (mechanism: 36.25%), and ~11% at fuzz 20 on both — so the **fuzz tradeoff is real on the actual gem**: a noise-suppression knob measurably eats a real regression. (Mechanism vs gem differ slightly in absolute suppression because Chrome and Playwright draw the gradient at slightly different contrast — the *direction* is identical.)

**`v08` and `v11` exposed real Wraith's instability.** Two independent real-Wraith captures of `v08-cta-removed` at the same 1280px config disagreed wildly — **0.08% vs 30.77%** — and `v11-broken-link` landed at **1.35%** of *spurious* churn both times where the page should be pixel-identical. Cause: real Wraith Chrome mode does **not** freeze animations, fonts, or lazy-loaded images before shooting, so full-page height and content vary run-to-run; ImageMagick then extends to the taller image and counts the mismatched tail. This is a genuine Wraith weakness, and it's exactly what our mechanism reproduction removes by stabilizing the page first (its `v08`/`v11` numbers are deterministic). It does **not** change any conclusion: a pixel diff — real or reproduced, stable or noisy — still cannot see the broken link, the console error, the missing `lang`, or any URL/transport defect.

## Honest takeaway

For *purely visual* regressions, Wraith's pixel-diff mechanism and matchy land in the same place — both catch every visible change and both correctly ignore the render-equivalent rewrite. Wraith's advantage is conceptual simplicity and pixel-truth; its hard limits are (1) it only knows *that* pixels moved, never *what* or *why*, (2) it is **blind to every non-visual defect** — broken links, console errors, accessibility, and all URL/transport hygiene — and (3) the real tool's default engine is **dead on modern ARM** (Chrome mode runs only after manual chromedriver surgery) and the project is **archived (Jan 2026)**. matchy subsumes the visual signal (it ships its own pixel-region layer) and adds the semantic, transport, runtime, and a11y channels Wraith structurally lacks, with typed output an agent or CI can act on.
