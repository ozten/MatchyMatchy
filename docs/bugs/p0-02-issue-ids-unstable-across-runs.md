# Issue: Issue ids unstable across runs; --baseline accept-lists don't hold

**Status:** FIXED (2026-06-11 — see ROOT-CAUSE-AND-PLAN.md and docs/golden-changelog.md)
**Found:** 2026-06-11, during a real migration gate (Webflow staging page vs local Next.js port)
**Severity:** P0 — the `--baseline` accept-list workflow is broken for the error class it matters most for; CI gates cannot be expressed as durable acceptances
**Area:** issue-id hashing / baseline / accept-list

---

## Summary

Issue ids are generated by hashing the issue's content, and that hash incorporates the
raw `href` attribute captured from the page. The Webflow staging site injects HubSpot
tracking query parameters (`__hstc`, `__hssc`, `__hsfp`) into external links
nondeterministically — present on some loads, absent on others. Because these parameters
change the href string, they change the hash, which changes the issue id.

An accept-list of all 129 error-severity ids was generated from run `matchy-nr-2`
(runId `2026-06-11T17-12-49Z`). The very next run minutes later, `matchy-nr-3`
(runId `2026-06-11T17-15-32Z`), used that list as `--baseline`. Of the 129 ids, 120
were correctly suppressed. The remaining 9 matched nothing — they were logically
identical issues (same link text, same destination domain) but had been re-emitted
under new ids because the href in the second capture was clean (no tracking params).
Four of those nine are the highest-signal findings of the run — the `missing_link`
errors for Press Kit, Developer Docs, Hiya Blog, and Partner Program — which are
expected 404-equivalent dev-environment differences that should be permanently
accepted.

The net result: `--baseline` cannot express durable acceptances for the exact issue
types that need them most (link-target differences, expected 404s, dev-only protocol
differences). Accept-lists must be regenerated from scratch on every run, making
them useless as a CI gate.

## Reproduction

```bash
# Step 1: capture a baseline run and extract all error ids
matchy run \
  --old "https://hiya-com-temp-43830deaa570809d11aa88b1f.webflow.io/products/connect/number-registration" \
  --new "http://localhost:3001/products/connect/number-registration" \
  --profile content-structure \
  --output /tmp/run-a

python3 -c "
import json
issues = json.load(open('/tmp/run-a/diff-result.json'))['issues']
ids = [i['id'] for i in issues if i['severity'] == 'error']
print('\n'.join(ids))
" > /tmp/baseline-ids.txt
echo "Captured $(wc -l < /tmp/baseline-ids.txt) error ids"

# Step 2: immediately run again with that baseline
matchy run \
  --old "https://hiya-com-temp-43830deaa570809d11aa88b1f.webflow.io/products/connect/number-registration" \
  --new "http://localhost:3001/products/connect/number-registration" \
  --profile content-structure \
  --baseline /tmp/baseline-ids.txt \
  --output /tmp/run-b

# Step 3: check how many ids survived into active errors
python3 -c "
import json
r = json.load(open('/tmp/run-b/diff-result.json'))
print('active errors:', sum(1 for i in r['issues'] if i['severity'] == 'error'))
print('suppressed:', r['suppressed']['count'])
"
```

The number of surviving active errors varies by run depending on whether HubSpot
tracking params were injected. When injected in run A but not run B, each affected
link produces a new id that the baseline does not cover.

## Expected

- Issue ids should be stable across runs for logically identical findings. Two
  `missing_link` issues with the same anchor text and the same destination hostname
  (modulo query string tracking noise) should produce the same id.
- Accept-lists generated on one run should suppress the same logical issue on all
  subsequent runs, without requiring regeneration.
- A CI gate built on `--baseline` should not flap because the source page's CDN
  injected tracking parameters on one load and not the next.

## Suggested fix direction

1. **Strip query strings before hashing hrefs.** For all issue types whose id hash
   incorporates a URL field (`href`, `src`, `rawHref`), normalize the URL to
   scheme + host + path before hashing. Query parameters — including tracking params
   like `__hstc`, `__hssc`, `__hsfp`, `utm_*`, `fbclid`, `gclid` — are volatile
   session data and should not contribute to id stability.

2. **Hash only stable structural fields.** The id for a `missing_link` issue should
   be derived from: `{type, anchor_text, nearest_heading, landmark_role}`. The href
   itself (even normalized) is unstable because it participates in the match that
   determines the issue exists; once the match assignment has fired, the identity
   should be anchored to the structural context of the missing node, not its captured
   URL.

3. **Native pattern-based suppression rules (alternative / complementary).** Add a
   `--baseline-rule` mechanism that suppresses by predicate rather than by id, e.g.:

   ```json
   { "type": "missing_link", "anchorTextPattern": "Press Kit" }
   { "type": "missing_link", "landmarkRole": "navigation" }
   ```

   This survives any id drift because it matches on the properties the developer
   actually cares about, not an opaque hash.

4. **Accept-list validation warning.** When `--baseline` is passed and more than N%
   of the provided ids match nothing in the current run's issue set, emit a warning
   that the accept-list may be stale and suggest regenerating it or switching to
   pattern-based rules.
