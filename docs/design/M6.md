## 1. What this milestone is (and is not)

M6 is a **gate**, not a feature. Its outputs are:

1. A **written calibration note** (`docs/calibration-note.md`) recording: the real pair(s) run,
   the triaged DiffResult, observed false positives/negatives, and the **frozen** values of every
   matcher/visual constant — with evidence for keeping or changing each.
2. **Frozen defaults** in `packages/analyze/src/config.rs`, annotated as frozen-at-M6.
3. Resolution of the three standing conditions (§5–§7 below), which must land **before** the
   calibration runs so the runs exercise final code.

No new diff capability is added. The capability-probe work the stale prompt describes is NOT
built (spec §2 defers it; §7.3 forbids emitting those types in v1).

## 2. The real pair (what "the actual migration" means here)

This repo has no customer migration; the project's real target page — the page the entire
testbed golden was captured from — is `https://www.hiya.com/products/connect/branded-call`.
That page has genuinely changed over the past year (Wayback CDX: 16 snapshots Dec 2024 →
May 2026; payload 13 KB → 52 KB; title changed from "Hiya Connect Branded Call: Go beyond an
answer rate" to "Branded Caller ID: Boost Answer Rates | Hiya"). A temporal pair of that page
is therefore a real old/new pair with real CMS drift, a real DOM rewrite, and real third-party
noise — exactly the failure surface §12 M6 wants the thresholds tuned against. Three pairs,
each isolating one calibration axis:

| id | old | new | axis |
|---|---|---|---|
| **R1** (primary) | `https://web.archive.org/web/20250603143211if_/https://www.hiya.com/products/connect/branded-call` (verified 200, June-2025 build) | `https://www.hiya.com/products/connect/branded-call` (live) | real drift: true positives + identity-matching stress across a year of edits |
| **R2** (noise floor) | live URL | same live URL | every emitted issue is by definition a false positive; calibrates visual thresholds + matcher stability under runtime-injected content (GTM, Weglot, HubSpot, cookie UI) |
| **R3** (staging-vs-prod analog) | `http://localhost:3000/` (frozen golden, third-party-stripped — the "clean staging" side) | live URL | third-party-noise handling: what hide/mask config a real migration run needs |

Scoping decisions, recorded here deliberately:

- **Desktop viewport only** (`--viewport desktop=1440x1000`) for all three pairs. Mobile doubles
  capture cost and Wayback flake risk without adding calibration signal; first real production
  use calibrates mobile. Recorded in the note.
- **R1 snapshot choice:** `20250603143211` (12 months back — large but explainable drift).
  Fallback ladder if Wayback capture fails (networkidle never settles / asset latency):
  (a) retry with `--no-freeze-time` (the §4.2 escape hatch exists for exactly this);
  (b) nearer snapshot `20251126042105`; (c) if Wayback is unusable entirely, R3 + R2 become the
  gate pair and the note records why (R3 is still a real pair: a frozen capture of the
  production page vs. the live production page).
- **First runs use no hide/mask** — calibration wants to see the raw noise first. Selectors are
  then added only where triage identifies volatile regions (cookie UI, injected widgets), and
  every added selector is recorded in the note as part of the recommended migration config.
- Both R1 sides are operator-supplied input URLs, so §10.3 same-registrable-domain probing
  covers `archive.org` (old side) and `hiya.com` (new side). Expect probe latency against
  Wayback; probe-timeout-induced `broken_link` FPs are a calibration finding, not something to
  pre-suppress.

### Run + archive protocol (determinism-preserving)

1. `matchy --old <old> --new <new> --out calibration/.capture/<pair>/ --viewport desktop=1440x1000`
   — once per pair. Capture happens **once**; tuning never re-captures.
2. Copy each pair's `diff-result.json` to `calibration/<pair>/diff-result.json` (committed).
   Bundles + PNGs stay local under `calibration/.capture/` (gitignored — live pages are not
   reproducible anyway); the note records their SHA-256s and sizes so the run is auditable.
3. All re-analysis during tuning runs `matchy analyze --old-bundle … --new-bundle …` against the
   archived bundles — pure, deterministic, cheap.
4. Determinism evidence: run `matchy analyze` twice on R1's bundles → byte-identical DiffResult
   modulo `runId` (the §3.3 invariant exercised on real-world-sized input, ~order-of-magnitude
   larger node streams than the testbed).

## 3. Triage taxonomy and gate criteria

Every issue in each DiffResult is assigned exactly one bucket (the note carries the table;
counts by type × bucket):

| bucket | meaning | consequence |
|---|---|---|
| `TP-defect` | would be a migration defect if this were a migration | none — tool correct |
| `TP-drift` | real change, legitimate CMS drift (spec §3.3 leak 3) | none — tool correct; baseline-list material post-M8 |
| `FP-tool` | tool is wrong (mis-pair, double-count, wrong evidence) | fix the code, re-analyze from bundles |
| `FP-noise` | capture/environment artifact (injected widget, animation residue, pixel AA) | mask/hide/threshold material; tuning lever |
| `archive-artifact` | exists only because the old side is served by Wayback (rewritten canonical, archive asset 404s) | explained in note; not counted against the tool |

**Gate pass criteria** (the spec's "no unexplained missing/added floods", made mechanical):

- R1: every `missing_*`/`added`-class issue traces to a visible old/new content difference
  (TP-drift or TP-defect) — zero unexplained `FP-tool` missing/added after fixes.
  `component_*` issues must not be manufactured by drift (M5's stage-1-only rule under stress).
- R2: target is **zero** content/structure/style issues. Anything emitted is triaged; visual
  issues from live-page nondeterminism are acceptable only as low-confidence/info or as
  documented mask recommendations.
- R3: content/structure parity with R2's conclusions once recommended hide/mask config is
  applied; the surviving delta must be explained by the documented golden strips
  (CAPTURE-NOTES.md) and third-party injections.

## 4. Tuning rules (what may move, and what it costs)

Levers, per spec §12 M6: per-kind identity weight tables, `IDENTITY_FLOOR`, `TIE_MARGIN`,
`MATCH_FLOOR`/`NO_MATCH_CEIL`, `STAGE2_*`/`TIEBREAK_*`, `VISUAL_THRESHOLD`, `MIN_REGION_AREA`,
`SEQ_MIN_DISPLACEMENT`.

- A constant changes **only** when a triaged FP/FN demonstrates the current value wrong, and the
  note records: the issue(s), the old value, the new value, and why the new value fixes the
  class rather than the instance.
- After any change: full testbed re-verify. Expected-issues files are the hard constraint —
  a tuning change that reds any intent check is rejected outright (the testbed encodes audited
  ground truth; calibration must not regress it). Byte-golden shifts caused by an accepted
  tuning change follow golden discipline: changelog entry + golden-auditor APPROVE + re-record.
- If the defaults survive triage with no demonstrated FP/FN, **freezing them unchanged is the
  expected outcome** — the gate's value is the evidence, not movement for its own sake.
- Freeze mechanics: a comment block at the top of the matching/visual constants in `config.rs`:
  `// FROZEN at M6 calibration (docs/calibration-note.md) — changes require recalibration.`

## 5. WP-A (code, pre-calibration): suffix-aware crop artifacts — M5 auditor follow-up (b)

**Defect.** `lib.rs` (visual region loop, ~lines 169–200) writes crop PNGs and stamps
`evidence.artifacts` paths using the issue id **before** `resolve_id_collisions` runs (lib.rs:302).
Colliding region issues (same type+viewport+anchors hash — common for weak-anchor regions) all
write `<base-id>_{old,new,diff}.png`: each write overwrites the last, so n−1 of n distinct
region crops are destroyed and every collided issue references the survivor's pixels. Live in
the recorded goldens today: v03 has `issue_a609a79ce17b-2`…`-19` — 18 issues, 3 surviving crop
files. Real-pair runs will collide far more; this must be fixed before calibration.

**Fix (design):** in the visual region loop, build the issues first with crops **deferred**:
keep `(issue_index, region_bbox)` aside; after `resolve_id_collisions(&mut issues)` (the lib.rs:302
call — note semantic_diff has its own internal call at semantic_diff.rs:3012 which is unaffected;
only visual issues carry crops), write each crop as `<final-id>_{old,new,diff}.png` and patch
`evidence.artifacts` with the final paths. Determinism: collision suffixes are already assigned
in total order (issue.rs); iterating the saved index list in ascending issue index is stable.
No filename changes for non-collided issues.

**Golden impact (register):** artifact-path strings (and on-disk crop names) change for the
suffixed issues in v02, v03, v04, v07, v12, v19. No id, anchor, severity, confidence, count, or
order changes. Re-record those six goldens after intent checks pass; changelog + golden-auditor
APPROVE required (behavior change, M5 audit follow-up as justification).

**Unit test:** two synthetic colliding visual issues → distinct final ids `x`, `x-2` and distinct
artifact paths `x_old.png` / `x-2_old.png`, files both present with different bytes.

## 6. WP-B (code, pre-calibration): unify `locale` stamping — M5 auditor follow-up (a)

Every emitter stamps `issue.locale = new_lang` (new page `<html lang>`) except
`sequence_diff.rs`, which leaves `None`. Fix: thread `new_lang` into `sequence_issues(..)` and
stamp it on `component_reordered`/`component_swapped`, matching the convention everywhere else
(semantic_diff, style_diff, hygiene, visual all use new-page lang; v18 correctly shows `en`
from its 404 page).

**Golden impact:** exactly one field in one file — v07's `component_swapped.locale`
null → `"en-US"`. Re-record v07 (shared with WP-A's v07 re-record); changelog + audit.

**Unit test:** sequence differ emits issues carrying the supplied lang.

## 7. WP-C (expectations): tighten hygiene status bands — standing condition from testbed build

The testbed-build audit's standing condition: at M6, tighten `statusIn: ["warn","fail"]` on the
hygiene variants if the implemented §9 default profile maps hygiene to fail. It does: all four
hygiene-variant goldens (v14 `url_trailing_slash`, v15 `locale_separator_invalid`,
v16 `locale_case_invalid`, v17 `url_redirect_chain`) emit severity `error` under
`content-structure`, producing `status: "fail"` (v18 was authored `["fail"]` already).

Change `statusIn` to `["fail"]` in v14–v17 `expected-issues.json`. This is a **tightening**
(strictly stronger assertion — the spec-correct §9 mapping `hygiene → fail` now excludes a
status the profile can't produce), not an accommodation. Golden discipline applies in full:
draft → golden-auditor → APPROVE → apply + changelog entry. v16/v17 are included beyond the
condition's literal v14/v15 because they assert the identical band for the same category —
leaving them loose would be the inconsistency.

## 8. WP-D: calibration runs + note (the gate itself)

Sequence (after WP-A/B/C are merged and the testbed is green):

1. Run R1, R2, R3 per §2 protocol (test-runner executes; capture failures follow the §2
   fallback ladder).
2. I triage every issue per §3 (orchestrator-owned — this is the judgment work), reading
   DiffResults via targeted queries; crops consulted where pixel evidence decides a bucket.
3. Apply §4 tuning loop if triage demands it (re-analyze from archived bundles only).
4. Write `docs/calibration-note.md`:
   - pairs, URLs, snapshot ids, capture dates, bundle SHA-256s, determinism-step status from
     each bundle, environment fingerprint (and the R1 fingerprint-mismatch warning behavior);
   - triage tables (type × bucket, with per-issue notes for missing/added/structure classes);
   - FP/FN findings and any constant changes (or the evidence for no changes);
   - the frozen constant table (every §4 lever with its final value);
   - recommended real-migration run config (hide/mask selectors, probe caveats);
   - explicit DoD statement: triaged DiffResult committed at `calibration/r1-…/diff-result.json`,
     awaiting team sign-off in review.
5. Annotate `config.rs` frozen block; `.gitignore` += `calibration/.capture/`.

## 10. Risks

- **Wayback capture flake** — fallback ladder in §2; worst case R3+R2 carry the gate with the
  substitution recorded.
- **Live-page drift during the milestone** — R2/R3 captures of the live page happen in one
  session, same day; bundles archived immediately; tuning never re-captures.
- **hiya.com anti-bot / consent geo-variance** — if the live capture is blocked or renders a
  consent interstitial, hide/click selectors (`--click` exists) are applied and recorded; if the
  page is fully blocked, R1-old↔R3-old (archive vs. frozen golden) still forms a real pair.
- **Probe storms against archive.org** — probe concurrency is already capped; if HEAD probes
  flood or hang, the finding is recorded and probe-derived FP types are triaged as
  archive-artifact rather than silently suppressed.
